# 가게별 업무 앱 실행

## 한 장 요약

발급받은 계정으로 로그인하면 가게 정보를 세 단계로 저장한 뒤 소식·리뷰·이번 주 가용 시간을 입력하고,
작성된 문안을 확인한 뒤 최종 검토, 문안 복사·ZIP 저장과 직접 게시 보고까지 진행할 수 있다.
일별 숫자의 입력·정정, 주간 보고서 검토, 실제 승인 문안의 피드백 확인과 명시적 반영도 같은 계정에서 진행한다.
사장님 브라우저에는 CLI 설치나 공급자 키 입력이 필요 없다.
현재 웹 입력은 네이버 소식 1건, 선택 사진 1장과 제공 리뷰의 답글을 지원한다.
생성된 문안을 직접 고치고 자동저장·버전 복원 후 확인할 수 있다. 명시적 재작성과 기간·상태별 보관함도 제공한다.
`aicmo serve`는 기존 시안 UI이고, 이 앱의 실행 명령은 `python -m aicmo.store_app`이다.
G02와 공개 유료 운영 판단은 OPEN이다.

## 운영자가 준비할 것

이 저장소의 `uv sync` 환경을 준비한다. 신규 사장님은 웹 입력으로 가게별 `config.md`,
`brand-guidelines.md`, `pricing-rules.md`, `copy-patterns.md`를 만들 수 있다.
기존 가게는 준비된 `clients/<slug>/` 원천 파일을 연결한다. `aicmo onboard --client ... --from ...`
명령은 [온보딩 입력 계약](../src/aicmo/onboarding.py)의 필드에 맞춘 실제 확인 답변 파일로 실행한다.
가게 콘텐츠 원천은 이 파일이며 앱의 Store는 소유권·표시 이름·slug 인덱스다.

PowerShell에서 다음 환경을 설정한다. 아래 키는 출력하지 않고 현재 프로세스 환경에만 넣는다.
재시작에도 같은 키를 사용하도록 운영 환경의 비밀 저장소에서 보관·주입한다.
매번 키를 다시 만들면 기존 세션을 사용할 수 없다.

```powershell
uv sync
$env:AICMO_REPO = (Get-Location).Path
$env:AICMO_WEB_SECRET_KEY = (uv run python -c "import secrets; print(secrets.token_urlsafe(64))")
$env:AICMO_WEB_LOCAL = '1'
uv run python -m aicmo.store_app migrate
uv run python -m aicmo.store_app createsuperuser
uv run python -m aicmo.store_app runserver 127.0.0.1:8766 --insecure
```

`http://127.0.0.1:8766/operator/`에서 운영자 계정으로 로그인한다.
Django Users에서 사장님 계정과 비밀번호를 만든다. 신규 계정은 로그인 후 **가게 정보 입력·이어 쓰기**로 시작한다.
이미 파일을 준비한 가게는 Stores에서 그 계정과 가게 slug를 연결한다.
Store 생성 후 slug는 관리자 화면에서도 변경할 수 없다. 잘못된 연결은 운영자가 검토한다.
사장님에게 staff/superuser 권한을 주지 않는다. `operate_stores` 권한은 모든 가게 업무에 접근하므로
그 역할이 필요한 운영자에게만 부여한다. staff만으로는 다른 가게 업무 권한이 생기지 않는다.
계정 복구는 관리자가 비밀번호를 재설정하며 자체 공개 가입·메일 발송·복구 서비스는 아직 없다.
업무 저장 직전에 계정 활성 상태·현재 가게 소유권·운영 권한을 다시 확인한다. 요청 중 권한이 바뀌면
처음에는 내용을 확인했더라도 저장이 거절될 수 있다. 이미 내려받은 파일은 사후 회수하지 않는다.

작성·검토 명령은 운영자가 별도 터미널 환경에 JSON 배열로 설정한다.
각 명령은 stdin의 작업 요청을 읽고 stdout에 결과만 반환해야 한다.
CLI 별칭이 아닌 범용 명령 어댑터를 쓰므로 사용하는 CLI의 비대화형 인자를 함께 지정한다.
검토 명령은 `aicmo.reviewer-decision.v1` 계약을 따라야 한다.
실제 실행 계정·데이터 처리 권한과 명령 동작을 확인한 뒤 연결한다.

```powershell
# 준비한 JSON 파일은 ["실행파일의 절대경로", "비대화형 인자", ...] 형식이다.
$env:AICMO_WEB_EXECUTOR_CMD = Get-Content .aicmo/executor-command.json -Raw
$env:AICMO_WEB_REVIEW_CMD = Get-Content .aicmo/reviewer-command.json -Raw
uv run python -m aicmo.store_app work
```

worker 터미널에도 같은 `AICMO_REPO`, `AICMO_WEB_SECRET_KEY`, 로컬 개발 설정이 필요하다.
`work --once`는 대기 작업을 최대 한 건 처리하고 종료한다.
공급자 설정이 없으면 새 문안 생성 요청을 받지 않지만 가게 정보 준비·대기 작업 확인·저장된 취소 요청 처리는 가능하다.
상품 한도는 기존 [실행팩 사용법](LOCAL_PACK.md)의 수량 한도 명령으로 설정한다.
공급자 청구액·비용 상한과 상품 팩 수량은 서로 다른 값이다.

## 사장님이 사용하는 순서

신규 가게는 먼저 **가게·동네 → 상품·가격·영업시간 → 목적·채널·시간**을 입력한다.
후기·홈페이지·고객 특징을 모르면 비워 둔다. **임시 저장하고 나가기**, **저장하고 이전으로**를 지원하며
다시 로그인해 이어 쓸 수 있다. 마지막 확인 화면에서 수정 링크를 사용하고, 확인 체크 후 **확인하고 가게 준비**를 누른다.
worker가 처리하는 동안 입력은 보존된다. **준비 상태 새로 확인**을 누르면 완료 후 첫 요청 화면으로 이어진다.
대표 상품을 이번 주 소식으로 자동 등록하거나 문안 작업을 자동 생성하지 않으므로 실제 알릴 소식을 직접 입력한다.
완료한 가게 프로필 수정은 현재 운영자에게 요청한다. 최초 온보딩은 계정당 한 번이며 기존 가게 파일을 덮어쓰지 않는다.

1. `/login/`에서 발급받은 계정으로 로그인하고 오늘 화면의 준비할 소식을 고른다. 진행 중인 작업이 있으면 먼저 **진행 중인 작업 이어 보기**로 이동한다.
2. 실제 확인한 소식과 답글을 쓸 리뷰를 입력한다. 고객 이름·연락처를 제거하고 시간은 5~240분으로 적는다.
3. 접수 뒤 화면을 닫아도 작업이 보관된다. **상태 새로 확인**에서 작성된 내용을 확인한다.
4. 필요하면 **문안 직접 고치기**에서 수정한다. 원본은 **확인하고 최종 검토 요청**, 저장된 수정본은 **저장한 수정본 미리보기·확인**에서 확인 체크 후 최종 검토를 요청한다.
5. **저장 가능** 상태에서 승인 문안 복사 화면을 연다. 문안을 복사하거나 ZIP을 저장하고, 네이버에서 직접 게시한 뒤 게시 날짜를 기록한다.

20분 미만이면 답글은 앞의 최대 2개, 그 외에는 최대 5개다. 입력 오류는 같은 화면에서 답변을 유지한다.
직접 수정은 제목·본문·행동 안내·기간·리뷰 답글에 한정한다. 원문 사실·참조 번호·사진 선언은 바뀌지 않는다.
새 가격·행사·사진처럼 확인된 사실이 달라지는 변경은 새 요청으로 확인해야 한다.
승인한 해시와 최종 검토·다운로드 시점의 실제 파일이 다르면 저장을 차단한다.
WARN·데모·검토 실패를 저장 가능으로 표시하지 않는다. ZIP 저장은 외부 게시 완료가 아니다.

### 문안 저장과 이전 버전 복원

**문안 직접 고치기**는 사장님 확인을 기다리는 작업에서 사용할 수 있다. 입력을 멈추면 현재 수정본 하나를
자동저장하며 상태를 화면에 표시한다. **이 버전 저장**을 누르면 다시 돌아갈 수 있는 버전으로 보관한다.
JavaScript가 꺼져 있어도 이 버튼으로 저장할 수 있다. 직접 수정·자동저장·복원은 모델을 호출하거나 작성 건수를 추가로 사용하지 않는다.

**저장한 버전**에서 처음 생성된 문안 또는 보관한 문안을 복원할 수 있다. 복원 직전의 자동저장 문안도 버전으로 남긴다.
보관 버전은 작업당 최대 100개다. 한도에 도달해도 현재 문안 자동저장과 확인은 가능하며 기존 버전을 자동 삭제하지 않는다.
수정본은 서버에 보관하므로 다시 로그인해 이어 쓸 수 있다. 브라우저 영구 저장소에 문안을 추가로 보관하지 않는다.

다른 창에서 먼저 저장했거나 작업이 처리 중이면 저장을 거부한다. 안전하게 확인한 입력은 같은 화면에 남기며
최신 작업을 별도 탭에서 확인하도록 안내한다. 비밀정보·숨은 문자·입력 상한 위반은 원문을 다시 표시하지 않는다.
저장된 수정본이 있으면 원본 승인 버튼으로 넘어갈 수 없다. 미리보기에서 확인한 버전만 worker에 전달하며
확인 후에는 편집이 잠긴다. 최종 검토가 통과해야 그 수정본이 담긴 ZIP을 저장할 수 있다.

### 실제 사진과 다시 작성하기

새 요청에서 JPEG/PNG 사진 1장을 선택하고 설명, 직접 촬영 또는 사용 허락, 개인정보 확인을 입력한다.
사진은 20 MiB·2,400만 화소 이하의 단일 프레임만 받는다. 방향을 반영하고 긴 변을 최대 2,048픽셀로 줄인 뒤
원본 메타데이터를 제거한 PNG를 보관한다. 파일 오류 뒤에는 문안 입력을 확인하고 사진을 다시 선택한다.
사진 수신 단계에서도 파일 1장·20 MiB 상한을 적용한다. 큰 파일·여러 파일·완성되지 않은 전송은
작업으로 접수하지 않고 다시 선택할 안내를 표시한다. 모든 사진은 Django 임시파일 경로를 거치며
정상·거절·파싱 오류 요청 뒤 해당 수신 임시파일을 정리한다. 전체 HTTP 본문·수신시간·동시 요청의
총 임시 저장량과 프록시/WSGI 선행 버퍼 한도는 실제 배포에서 별도로 설정·확인해야 한다.
작성 결과와 수정본 확인 화면에 같은 사진을 표시한다. 사진 속 개인정보와 사용 권리의 진위는 사장님이 확인한다.
원본 파일명은 manifest에 저장하지 않는다. 정규화 사진과 중단된 요청의 미채택 사진은 자동 삭제하지 않는다.

**짧게 · 친근하게 · 가격 수정으로 다시 작성**은 별도 새 작업이다. 먼저 현재 수정본을 저장하고 기존 작업의 취소를
완료한 뒤 다시 작성 화면을 연다. 현재는 승인 전 취소된 소식 한 건의 웹 작업만 지원한다.
짧게·친근하게는 같은 사실을 사용한다. 가격·기간·혜택 수정은 이번 소식의 사실 전체를 새 값으로 입력하고 직접 확인한다.
새 요청 미리보기에서 변경할 사실과 기준 문안을 확인하고 사용 건수 동의 후 요청한다. 기존 사진이 있으면 그대로 이어 쓴다.
사진 교체는 기존 작업 취소 완료 후 새 소식 만들기에서 선택한다.

미리보기는 모델을 호출하지 않는다. 새 요청은 기존 worker와 수량 한도를 사용하고 이미 사용한 작성 시도는 되돌리지 않는다.
같은 확인 요청의 재전송은 같은 Job을 반환한다. 새 AI 결과도 사장님 확인과 최종 reviewer를 다시 통과해야 저장할 수 있다.
기존 결과나 저장된 수정본을 새 결과로 덮어쓰지 않는다.

### 작업 보관함

홈의 **모든 작업 · 기간과 상태로 찾기**에서 내 가게, 상태, 한국 시간 기준 시작일·종료일로 찾는다.
시작일과 종료일을 모두 포함하며 20건씩 최신 순서로 표시한다. 페이지 이동 시 검색 조건을 유지한다.
잘못된 날짜나 없는 페이지는 검색 조건을 다시 확인하도록 안내한다.

### 오늘 할 일과 사용 가능 건수

가게 설정의 목적·주당 시간을 참고해 최대 세 개의 준비 카드를 보여 준다. 현재 지원하는 프로필 형식에서
두 값을 확인할 수 없으면 기본 안내와 수정 가능한 20분을 제안한다. 확인한 대표 상품·가격·영업시간도
이번 주 사실로 자동 입력하지 않는다. **입력 전에 소식 종류 고르기**에서 신메뉴·영업/휴무·행사·리뷰 도움말을 선택할 수 있다.
입력 전에 종류를 고른다. 종류 링크를 다시 열면 아직 제출하지 않은 입력은 보존되지 않는다.
현재 모든 진입은 소식 1건, 선택 사진 1장과 제공 리뷰의 답글을 준비한다. 리뷰만 만드는 기능은 아직 없다.
알릴 소식이 없으면 오늘은 만들지 않아도 된다.

사용 건수 안내는 원장을 읽기만 하며 화면을 여는 동작으로 원장을 생성하거나 한도를 예약하지 않는다.
기존 SQLite WAL 원장을 읽을 때는 SQLite가 `-wal`/`-shm` 보조 파일을 만들 수 있다. 스키마·업무 기록을 쓰지 않는 논리적 읽기 전용이며 파일 시스템 쓰기가 전혀 없다는 뜻은 아니다.
기록 없음, 제한 미설정, 이번 달 한도 미설정, 조회 실패, 잔량 부족을 구분한다. 제한 미설정은 무료나 무제한 요금 약속이 아니다.
새 요청 가능 건수는 이번 달 한도에서 예약·저장 완료 건수를 뺀 값이며 작성 시도 잔량도 함께 표시한다.
요청 접수 때 다시 확인하고 실제 예약·작성 시도 차감은 worker가 처리한다. 화면을 연 뒤 한도가 바뀌면 작업이 중단될 수 있다.
진행 중인 요청이 있으면 새 요청 화면과 제출 모두 기존 작업으로 안내한다. 승인·저장은 새 요청 잔량과 별도로 기존 검증을 따른다.

## 승인 문안 복사와 직접 게시 보고

`/jobs/<작업 번호>/delivery/`는 현재 승인·최종 검토 PASS와 파일/사진 해시를 다시 확인한 뒤
ZIP에 들어갈 소식·답글의 평문을 보여 준다. 웹 Job과 엔진의 입력 전체가 다르면 복사 화면과 ZIP 저장을 거절한다.
화면 열기와 복사는 납품 파일 생성·새 작성·사용량 차감·게시 기록 저장을 하지 않는다.
SQLite의 읽기 조정용 WAL/SHM 보조 파일은 생길 수 있으며, 이것을 승인 자료나 원장 내용의 변경으로 세지 않는다.

복사 버튼은 클릭에 응답해 클립보드를 쓰고 성공한 뒤에만 완료를 알린다. 브라우저에서 허용하지 않거나
JavaScript가 꺼져 있어도 읽기 전용 문안 칸에서 직접 선택·복사할 수 있다. 사진은 텍스트 복사에 포함되지 않으므로
ZIP의 안내된 PNG를 직접 첨부한다. 네이버 스마트플레이스의 고정된 공식 링크는 새 탭에서 열린다.

실제로 게시한 뒤 각 문안의 **직접 게시했어요**를 눌러 한국 시간 기준 게시 날짜를 기록한다.
작업 생성일부터 오늘까지만 기록할 수 있다. 날짜 정정과 오기록 취소는 이전 이력을 보존하며 새 기록을 추가한다.
오기록 취소는 앱의 사용자 보고 취소이며 네이버 게시물 삭제가 아니다. 최신 20개 이력을 표시하고 이전 이력도 보관한다.
같은 요청의 재전송은 추가 기록을 만들지 않으며, 다른 탭에서 먼저 정정했다면 최신 화면을 다시 열도록 안내한다.

게시 보고에는 승인 묶음/문안 파일 해시·작업·항목·로그인 계정·기록 시각·게시 날짜를 저장한다.
게시 URL·고객 리뷰 원문·자유 메모는 받지 않는다. 복사·다운로드·채널 열기와 사용자 보고는 외부 게시 검증이 아니며,
문의·예약·매출·일별 게시 수나 KB 학습에 자동 반영하지 않는다. 게시 보고 보관·삭제는 G02의 별도 미완료 항목이다.
업데이트 시 기존 준비 명령의 `migrate`로 `0004_publicationreport`를 적용한다.

## 지속 작업과 복구 경계

### 숫자 기록·주간 보고서·문안 피드백

오늘 화면의 **게시·문의·예약 숫자 기록과 확인**에서 주의 월요일과 채널을 고른다.
하루의 게시·문의·예약·쿠폰 사용을 직접 입력하거나 CSV 1개를 미리 보고 확인해 저장한다.
숫자는 0~1,000,000의 정수만 받으며 빈칸은 미입력, 0은 확인한 0건이다.
CSV는 UTF-8 또는 UTF-8 BOM, 32 KiB 이하, 같은 주·채널의 최대 7일이며 열은 다음 순서다.

```text
date,channel,posts,inquiries,reservations,coupon_redemptions
```

확인 화면은 기존값과 입력값을 비교한다. 이미 기록한 날짜를 바꾸거나 미입력으로 되돌릴 때는
정정 확인도 필요하다. 파일에 없는 날짜는 지우지 않는다. 확인은 15분 동안 유효하며,
그 사이 다른 화면에서 값을 정정했다면 최신 숫자를 다시 미리 본다. 같은 확인 요청을 재전송하면
같은 숫자를 중복 저장하지 않는다. 입력 경로·기록 시각·수정 번호는 저장된 기록에서 확인하며
출처가 없는 이전 기록에 임의의 입력자나 시각을 붙이지 않는다.

저장한 숫자 화면은 관측 부분합과 지표별 **입력 N/7일**을 표시한다. 두 주 모두 7일이 입력되고
지난주 합계가 양수일 때만 증감률을 표시한다. 직접 게시 보고를 일별 게시 수로 자동 합산하지 않는다.
**확인한 기록으로 보고서 요청**은 접수 당시 두 주의 숫자와 출처를 고정해 최종 검토를 요청한다.
접수 뒤 숫자를 정정해도 기존 보고서는 바뀌지 않으며, 화면에서 정정 여부와 최신 기록 링크를 확인한다.
검토를 통과한 정확한 원문만 읽거나 Markdown 파일로 저장할 수 있다. WARN·실패·파일 변조는 저장 완료가 아니다.

보고서는 **숫자 요약 → 다음에 할 일 → 검토 원문** 순서로 보여준다. 요약의 네 지표와 입력 N/7일은
검토 당시 기록이며, 상단 바로가기로 각 부분에 이동할 수 있다. **검토한 보고서 원문 펼치기**를 누르면
전체 원문을 읽을 수 있고, 원문을 접어 두어도 같은 Markdown 파일을 저장할 수 있다.

보고서의 다음 행동 선택은 선호 영수증만 남긴다. 기록 확인·기존 소식 확인·실제 새 소식 입력 화면으로
이동하며 새 문안, 실제 게시, 성과나 학습 기록을 자동 생성하지 않는다.
승인 문안의 복사 화면에서 **이 문안의 사용 여부·수정 이유 남기기**를 열면 실제 사용 여부·관측일·이유·제안을 입력한다.
필요하면 같은 가게의 검토된 네이버 주간 보고서를 연결한다. 관측일은 해당 보고서의 주에 포함되어야 한다.
최근 보고서 최대 20개를 확인하며 전체 검토 근거가 6,000자를 넘으면 잘라 제출하지 않고 재확인을 안내한다.

피드백은 **후보 확인 → 사장님 승인 → 최종 검토 → 명시적 반영** 순서다.
원본과 실제 승인 문안, 연결한 보고서와 제안을 확인한 뒤 최종 검토를 요청한다.
검토 PASS 후 **확인한 피드백을 다음 문안에 반영**을 눌러야 기존 승인 피드백 KB에 저장된다.
같은 반영을 재전송해도 같은 기록을 중복 추가하지 않는다. 유효한 반영 기록이 있다는 표시가
다음 생성의 실제 사용을 보장하지는 않는다. 현재 사실·가게 지침을 우선하며 기존 학습 문맥은
최신 후보 20개 중 검증된 최대 5개만 참고한다.

업데이트 시 `migrate`로 `0005_job_workflow_id`를 적용한다. 기존 Job은 주간 실행팩으로 유지되고,
같은 큐에 주간 보고서와 문안 피드백이 추가된다. 보고·피드백에는 검토 명령만 필요하며
작성 명령을 호출하지 않는다. 최종 검토의 실제 사용량은 발생할 수 있고, 보고·피드백을 실행팩 상품
건수에서 임의 차감하지 않는다. 실제 제공 횟수와 요금은 운영자에게 확인한다.

새 작업 시작 전에 검토 설정을 사용할 수 없으면 안전한 실패 안내를 남긴다. 기존 엔진 실행이 있거나
확인할 수 없으면 실행을 실패로 단정하지 않고 현재 상태와 취소 경로를 유지하므로 운영자 확인이 필요하다.
숫자는 기존 엔진 성과 원장 하나에 저장하고 웹 DB에 복제하지 않는다. 보고 스냅샷·피드백·선호 영수증·
내려받은 사본의 보관/삭제와 실제 처리 근거는 운영자가 별도로 확인한다.

### 원장과 재개

- workflow와 프롬프트 변경은 기존 실행의 고정 명세와 다를 수 있다. 운영 환경 업데이트 전에 기존 버전에서
  진행 작업을 완료하거나 취소한다. 이미 명세가 바뀐 실행의 해시를 강제로 바꾸지 말고 운영자가 원래 버전에서 정리한다.
- 웹 원장 `.aicmo/web.sqlite3`: Django 계정·세션·가게 소유권·온보딩 draft·정규화 입력·Job·승인 요청·게시 보고/정정 이력.
- 엔진 원장 `.aicmo/runs.sqlite3`: 고정된 `web-<UUID>` 실행·단계·승인·납품 검토·수량 원장.
- 파일: 기존 `artifacts/`, `.aicmo/snapshots/`, 사진 저장소 등. 이 디렉터리를 웹 정적 파일로 노출하지 않는다.
- 같은 가게+제출 UUID+입력은 같은 Job을 반환한다. 다른 내용의 동일 키와 동시에 진행 중인 두 번째 작업은 거부한다.
- worker 파일 잠금은 저장소 전체에서 한 작업만 실행한다. 프로세스 종료 시 OS가 잠금을 해제한다.
  다음 worker는 저장된 running 작업을 재개하고, 기존 엔진 단계의 살아 있는 lease는 만료 전에 빼앗지 않는다.
  한 작업이 막히면 뒤 작업도 기다리는 단일 worker 구조다. 다중 서버·대규모 처리 전에는 큐와 DB를 재설계한다.
- HTTP 취소는 요청만 저장한다. worker가 이를 적용하며 이미 진행 중인 공급자 호출은 반환 시점까지 기다릴 수 있다.
  이미 완료된 납품은 완료 상태를 유지한다. 취소 상태를 검증하지 못한 경우 실패와 운영자 문의를 표시한다.
  모든 단계 성공 후 완료 기록 직전에 중단된 경우도 검토 증거를 다시 확인해 공급자 호출 없이 완료·수량 정산을 복구한다.
- 승인 요청은 문안·사진 manifest SHA와 로그인 계정의 확인 기록을 저장한다.
  엔진 승인 직후 중단되어도 같은 승인 기록을 확인한 뒤 재개한다. 두 DB의 원자적 동시 커밋을 가정하지 않는다.
- 수정본 적용은 파일 교체 전에 엔진에 정확한 문안·기준 버전·승인 의도를 기록한다. 중단되면 같은 기록만 복구한다.
  웹 실행별 OS 잠금이 worker와 CLI 변경을 직렬화한다. 미완료 수정 적용 중에는 다른 실행 변경을 막는다.
  취소 worker는 공급자 설정 없이 확정 수정 적용을 마친 뒤 취소할 수 있다. 실제 생성 재개는 기존 공급자 정책 검사를 유지한다.
  수정 적용 완료 후 파일·해시·승인 기록이 달라지면 납품/재개를 거부하며 다른 파일을 자동으로 정답 처리하지 않는다.
  내부 실행 번호·파일 해시는 형식/출처를 검증해 보존하고 고객 문안·설명·검토 사유와 분리하여 개인정보 처리한다.
- 자동 보관 만료·완전 삭제·백업 복구 UI는 아직 없다. 중단·실패의 원인은 운영자가 엔진 원장을 확인한다.
  과거 Job을 임의로 편집해 재실행하지 않고, 원인을 수정한 후 사용자에게 새 요청 경로를 안내한다.
- 엔진 오류·이벤트의 자유 설명은 인식 가능한 고객 연락처와 비밀값을 정리한다. 구조 ID·SHA·revision은
  일반 문장 마스킹으로 바꾸지 않는다. 기존 원장을 소급 삭제하거나 프록시/공급자 로그까지 정리한 것은 아니다.

### 가게 준비가 중단된 경우

온보딩 worker는 기존 `scaffold_client(pdf=False)`를 사용하며 모델·외부 사이트·PDF 변환을 호출하지 않는다.
`.aicmo/onboarding/<준비 UUID>/<시도 UUID>/`에서 8개 파일을 만든 뒤 경로·크기·SHA를 DB에 저장한다.
그다음 `clients/web-client-<UUID>/`, `knowledge-base/web-client-<UUID>/`를 각각 옮기고 검증하여 가게를 연결한다.
같은 manifest와 바이트가 이미 있으면 이어가고, 기존 파일이 다르거나 추가 파일·경로 재지정이 있으면 멈춘다.
DB와 파일 시스템의 동시 원자적 커밋은 제공하지 않는다. 중단된 worker는 `work` 재시작으로 재개한다.

manifest 기록 전 새 파일 생성은 최대 세 번이다. 미완성 디렉터리는 임의 삭제하지 않으며 횟수가 소진되면
사장님에게 운영자 문의를 안내한다. manifest가 저장된 경우는 같은 파일의 복구만 다시 시도하여 새 디렉터리를 늘리지 않는다.
운영자는 `/operator/`의 Onboarding drafts에서 준비 번호·상태·고정 실패 코드·시도 횟수를 읽을 수 있다.
이 화면은 답변·경로를 노출하거나 수정·삭제 기능을 제공하지 않는다. 담당 직원에게는 별도의 view_onboardingdraft 권한이 필요하다.

| 실패 코드 | 운영자가 확인할 것 |
|---|---|
| `invalid_input` | 확인 입력의 무결성, 계정 활성 상태와 가게 연결 변경. 원문 비밀정보를 로그에 복사하지 않음. |
| `prepare_failed` | 저장 공간·파일 권한과 시도 횟수. 부분 파일이나 원천 설정을 확인 없이 삭제하지 않음. |
| `profile_conflict` | 기록된 manifest와 staging/목적지 파일의 크기·SHA·파일 목록·경로 재지정 여부. 차이를 강제로 덮어쓰지 않음. |
| `store_changed` | 가게 연결 전에 계정 또는 기존 가게가 바뀌었는지 확인. 기존 연결을 유지하고 새 연결을 중복 생성하지 않음. |

실제 자료 보존·복구 판단은 운영자가 한다. 보관 만료/삭제 정책과 자동 복구 관리 UI는 별도 미완료 항목이다.
`web-client-*` 경로와 staging은 Git 제외되지만 이것이 보관 동의·백업 암호화·삭제 완료를 뜻하지 않는다.

## 인증과 배포

Django 내장 비밀번호·세션·CSRF를 사용한다. 세션은 최대 8시간이며 브라우저 종료 시 만료하는 쿠키를 쓴다.
계정 비활성화 또는 비밀번호 변경은 기존 로그인 검증에 반영된다.
로그인 실패는 15분 창에서 계정 5회·접속 주소 30회로 제한한다. 성공 로그인은 실패 횟수에 남기지 않는다.
제한 키는 HMAC이며 원본 계정명/IP를 별도 제한 테이블에 저장하지 않는다.
프록시 전달 헤더의 IP를 자동으로 신뢰하지 않으므로 프록시 뒤에서는 주소 제한이 공유될 수 있다.

개발 서버와 `AICMO_WEB_LOCAL=1`은 루프백 개발 전용이다. `--insecure`는 개발 중 Django 관리자 정적 파일을 제공한다.
운영에서는 이 설정을 제거하고 명시적 `AICMO_REPO`, 호스트 목록 `AICMO_WEB_HOSTS`, 영속 비밀 키를 설정한다.
HTTPS·Secure 쿠키·HSTS가 기본이다. HTTPS를 올바르게 식별하는 WSGI 서버 구성과 보호된 정적 파일 배포가 필요하다.
신뢰하지 않는 전달 헤더를 받아 HTTPS로 간주하도록 설정하지 않는다.
`python -m aicmo.store_app check --deploy`와 `collectstatic`을 실행하고 DB·업로드·백업의 OS 접근 권한을 제한한다.
외부 공개 서버 설치·계약·실제 사용자 보안/접근성 검증은 이 구현의 완료 증거에 포함하지 않는다.

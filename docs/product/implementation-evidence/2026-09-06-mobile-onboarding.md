# 모바일 가게 온보딩 연결 검증

## 한 장 요약

발급된 계정으로 가게·동네 → 상품·가격·영업시간 → 목적·채널·시간을 입력하고,
임시 저장·이전 이동·재로그인 복원·마지막 확인 뒤 실제 가게 원천 파일을 생성하도록 연결했다.
모르는 선택 항목과 후기·홈페이지 없음은 허용하고, 서버가 가게 ID와 소유권을 결정한다.
기존 Django 폼·DB·worker와 `scaffold_client(pdf=False)`를 재사용하며 새 의존성은 추가하지 않았다.
사용 방법과 실패 코드별 복구 확인은 [STORE_APP](../../STORE_APP.md)을 따른다.
G02·실제 고객 사용성·공개 유료 운영은 OPEN이다.

## 구현과 버그 수정

| 경계 | 구현 및 검사 |
|---|---|
| 임시 저장 | 계정당 draft 하나, SQLite IMMEDIATE 트랜잭션의 revision 비교. 두 탭·동시 최초 저장의 오래된 쓰기 거부, 로그아웃 후 복원, 이전 단계에서 수정한 값 유지. |
| 입력 | 필수/URL/가격/5~240분을 항목별 검증. 정상 폼 오류는 입력 유지. 비허용 필드·중복 필드·과대·숨은 문자·방향 문자·특수 줄 구분자·한 줄 항목 개행은 저장 거부. |
| 개인정보 | 한국어·영어 credential 라벨, URL userinfo, env: 접두어 우회, 전각 표기를 공통 secret 검사와 마스킹에 반영. 거부된 비밀 입력은 오류 화면에 반향하지 않음. 지원되는 고객 연락처는 기존 최소화 함수 재사용. |
| 확인 | 현재 revision과 체크가 있는 POST만 접수. queued 이후 웹 편집 금지, 확인 전 파일 생성 없음. 미입력은 미확인/후기없음/미입력, 시장 유형과 사실 상태는 unknown 가능. 확인 시각의 KST 날짜 사용. |
| 파일 준비 | UUID별 새 staging에서 config·브랜드·가격·카피·KB·primer HTML 8개 생성. DB에 상대 경로·크기·SHA manifest와 시도 ID를 먼저 기록. 모델·사이트 수집·PDF 호출 없음. |
| 복구 | clients/knowledge-base 디렉터리를 각각 이동하고 정확한 파일 목록/바이트를 재검증. manifest 기록 전·후, 각 이동 후, 가게 연결 전 중단을 재현. manifest가 있으면 재생성 없이 이어감. 기존 파일·extra/partial·변조·Windows junction 거부. |
| 재시도·진단 | 새 staging은 최대 3번, 기존 manifest 복구는 같은 파일 사용. 원문 예외 대신 고정 실패 코드. 운영자 관리자 화면은 번호·상태·코드·횟수를 읽기만 제공. 자동 삭제 없음. |
| 가게 연결 | 최종 짧은 DB 트랜잭션에서도 활성 신규 owner인지 재확인하여 Store와 complete 상태를 함께 기록. 기존 관리자 복수 Store 연결을 삭제하는 migration 없음. |
| Windows | 긴 staging의 디렉터리 생성에서 실제 WinError 206 재현. 공통 scaffold의 검증된 경로 I/O에 기존 native_io_path 적용. 반환 경로와 containment 검사를 유지하고 기존 갱신·롤백·KB 보존 검사 통과. |
| 모바일 | 서버 HTML과 내장 폼 사용. 선택 상자 최소 48px, 본문 크기 상속, 도움말 연결, 오류가 있는 추가 정보 펼침. 키보드 확인 및 390/1280px 가로 넘침 검사. |
| 첫 요청 | 가게 준비 완료 후 기존 소식 입력 화면으로 연결. 대표 상품을 이번 주 사실로 채우거나 Job을 자동 생성하지 않음. 직접 요청한 첫 문안부터 기존 승인·검토·ZIP 경로 사용. |

저장된 DB의 필드를 외부 관리자가 임의 변조하는 공격까지 신뢰한다고 가정하지 않는다.
웹에서 확정 후 편집을 막고 worker에서 입력 구조·개인정보 경계를 재검증하지만,
DB·파일을 함께 임의로 변경할 수 있는 OS 관리자의 악의적 행동은 이 검증 범위 밖이다.
자유 서술의 모든 개인정보를 익명화한다고 주장하지 않는다.

## 실제 로컬 실행 증거

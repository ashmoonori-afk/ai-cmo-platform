# 가게별 업무 앱 기반 검증

## 한 장 요약

Django의 내장 인증·세션·CSRF·관리자와 서버 템플릿으로 가게별 소식 작성 앱을 연결했다.
HTTP에서 DB에 Job을 접수하고 별도 worker가 기존 WorkflowRunner를 호출한다.
사장님은 문안을 확인하고 최종 검토 뒤 검증된 ZIP을 저장한다.
기존 `aicmo serve` 시안 도구와 구분되며 실행 방법은 [STORE_APP](../../STORE_APP.md)에 있다.
G02, 온보딩·편집·사진·성과의 웹 연결, 실제 가게 사용성·공급자 품질·유료 운영은 OPEN이다.

## 구현과 수정

| 경계 | 동작과 검사 |
|---|---|
| 가게 권한 | owner 또는 명시적 operate_stores 권한만 접근. 타 가게 Job·승인·취소·ZIP은 404. staff만으로 업무 접근을 허용하지 않음. |
| 인증 | Django 비밀번호·세션과 POST CSRF. 계정/주소 HMAC 실패 창. 정상 로그인 7회는 허용하고 5회 실패 뒤 제한, 계정 비활성화 세션 거부를 검사. |
| 접수 | 서버가 client/workflow/run/executor를 선택. 가게+UUID unique와 정규화 내용 일치 검증, 활성 작업 1개 제약. HTTP 동시 제출 멱등 검사. |
| 원장 | 앱 SQLite는 IMMEDIATE의 짧은 트랜잭션만 사용. engine 조회는 mode=ro로 열어 GET에서 초기화·마이그레이션하지 않음. |
| worker | 기존 OS 파일 잠금을 재사용. DB의 running 상태와 엔진 lease를 확인해 재개. 두 OS 프로세스가 동시에 실행되어도 생성 한 번. |
| 승인 | 엄격한 버전·문안 SHA·사진 SHA·로그인 계정·시각 계약. 저장된 승인 또는 입력 손상은 실패 처리. 엔진 승인 후 중단되어도 같은 영수증을 대조해 재개. |
| 취소 | HTTP는 의도만 저장하고 worker가 실행. 공급자 설정이 없어도 취소 가능. 호출 도중 취소·실행 전 취소·완료와 취소 경합 검사. |
| 결과 | 실제 문안·리뷰 답글·실행 계획 표시. 최종 PASS 증거와 파일/사진/명세 검증 후 POST에서 ZIP 저장. WARN·실패·데모를 납품 성공으로 표시하지 않음. |
| Windows | 실제 브라우저 실행에서 긴 경로의 `_pre_edit`·임시 파일 생성 실패를 재현. containment 검사와 원장 상대 경로는 유지하고 파일 I/O에 native extended path를 적용. 128자 run ID 승인 스냅샷 회귀 통과. |

독립 리뷰가 지적한 성공 로그인 누적 차단, 설정 없는 취소 실패, HTTP의 장시간 SQLite write lock,
GET 원장 초기화, 별도 OS worker 검증 누락을 수정했다. 작성·검토 서비스의 자격 증명은 브라우저에 받지 않는다.
추가로 모든 단계가 성공한 뒤 실행 완료 기록 직전에 중단되면, provider 없는 재개가 기존 실행 정책과 충돌했다.
`complete_verified_local_pack`은 현재 파일·명세·승인·최종 검토 증거를 검사한 뒤 기존 완료·상품 정산 경로만 호출한다.
공급자를 다시 호출하거나 실행 정책을 변경하지 않는다. 실제 완료 쓰기 지점에 예외를 주입하는 회귀를 추가했다.
제한된 단일 저장소 worker와 SQLite를 사용하므로 다중 서버 처리량을 검증했다고 주장하지 않는다.

## 합성 실행 증거

로컬 Django HTTP 서버와 Chromium에서 로그인 → 실제 폼 접수 → 두 별도 worker 동시 실행 → 문안 확인 →
승인 → 새 worker 프로세스의 최종 검토 → 실제 ZIP 저장 → 로그아웃을 실행했다.
합성 generator/reviewer만 사용했으며 실제 고객·모델 호출·외부 게시·결제는 수행하지 않았다.

최종 화면 성공 증거는 `artifacts/real-use-review/store-app-synthetic-v4/evidence.json`이다.
run은 `web-6b49bded2401478eb12d0862ce85d4d5`, 상태는 success이며 동시 worker 2개에서 생성 호출은 1회다.
묶음 SHA-256은 `a7e4791a5bda24e167e339905c412ea8c5230592925f4c81284aefb11a7cc701`,
ZIP SHA-256은 `b225c8fc649303820c146dd4691e229295bae1cc51c3bab1aeb0f24b90be2601`다.
ZIP 내부 파일 해시를 모두 재계산했다. 390/1280px에서 가로 넘침 없음과 실제 내용 표시를 확인하고 화면을 육안 검토했다.
키보드로 본문 바로가기 링크에 도달하고 Space로 확인 체크, Enter로 승인 요청을 수행했다.
한국어 단어 중간 줄바꿈을 줄이는 CSS도 이 최종 화면에서 확인했다.

Windows 긴 경로 회귀 포함 `tests/test_accept_edits.py` 8개가 10.51초에 통과했다.
앱 자동 검사는 기존 pytest에서 Django의 자체 테스트 DB 생명주기를 호출하며 별도 pytest 플러그인을 추가하지 않는다.
전체 회귀는 548 passed, 1 Windows 파일 symlink 생성 권한 skip(438.78초)이었다.
이후 완료 직전 중단 복구를 보완한 버전은 앱·quota·납품 검토 24개 표적 검사를 통과했다(139.77초).
전체 검사 수치는 이 마지막 국소 수정 이전의 증거다. Ruff와 basedpyright는 PASS다.
Django `check --deploy`는 0 issue, `makemigrations --check --dry-run`은 변경 없음이며,
wheel에 앱 템플릿·초기 migration·worker command가 포함됨을 확인했다. 공개 서버 배포 검증은 아니다.
최신 수량 정산 회귀를 포함한 앱 내부 Django 15개는 구현자 86.29초·독립 89.31초에 통과했다
(기존 pytest에는 wrapper 1개로 표시). 독립 quota+delivery 23개(65.14초), accept-edits 8개(13.27초)도 PASS다.
독립 reviewer의 마지막 판정은 PASS다. managed/unmetered 완료 직전 중단 복구와
managed reserved→consumed·납품 SHA를 재현했고, 변조는 실패 처리되어 새 소비로 승격되지 않았다.
손상된 완료 직전 실행은 운영자 복구가 필요하며 자동으로 성공 처리하지 않는다.
리뷰 원문은 ignored `artifacts/real-use-review/store-app-review.md`에 보관한다.

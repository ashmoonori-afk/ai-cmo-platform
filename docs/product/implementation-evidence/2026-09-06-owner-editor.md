직접 고치고 자동저장·명시 버전 저장·복원·수정본 확인·최종 검토·ZIP 저장으로 이어진다.
원문 사실·참조 번호·사진 선언은 서버가 보존한다. **G20 전체와 G02는 OPEN**이다.

## 구현과 수정한 결함

- Django `EditDraft` 하나를 기준 문안/spec/snapshot/시도 번호와 revision에 묶는다. 오래된 저장은 거부하며 같은 요청의 재전송은 중복 revision을 만들지 않는다.
- 자동저장은 현재 문안만 갱신하고 명시 저장·복원만 버전을 남긴다. 원본 포함 최대 100개를 보존하며 자동 삭제하지 않는다.
- POST의 필드 목록은 서버 Job의 brief에서 정한다. 제한·비밀정보 검사를 거친 입력을 잠금/파일 검증 전에 바인딩하여 JavaScript 없이 저장이 실패해도 안전한 입력을 같은 화면에 유지한다.
- 최초 편집과 기존 원본 승인은 같은 실행 잠금 안에서 Job 상태와 수정본 존재를 다시 검사한다. 저장된 수정본과 원본 승인 요청이 섞이는 경쟁을 차단했다.
- HTTP는 수정본과 확인 의도를 보관한다. worker는 엔진 receipt를 먼저 기록하고 정확한 파일·해시·승인을 적용한다. 파일 교체/해시/승인 직후 중단은 같은 receipt로 복구한다.
- 확정 수정 적용은 공급자를 호출하지 않는다. 공급자 없는 취소 worker에서도 적용 중단을 복구한 뒤 취소하며 실제 생성 재개에는 기존 실행 정책 검사를 유지한다.
- 수정 적용 완료 후 CLI 재승인이 실패하면서 다른 파일의 해시만 승인되던 경로를 차단했다. 승인 결정은 파일 해시 변경 전에 검사하며 확정 수정의 파일·해시·소유자 승인·사진 SHA가 달라지면 실행 재개를 거부한다.
- 웹 UUID 실행별 OS 잠금으로 worker/CLI 변경을 직렬화한다. 미완료 적용 receipt가 있으면 다른 변경을 막고 정확한 재적용만 허용한다. 취소는 확정 후 변조 상태에서도 납품을 막을 수 있다.

전체 회귀에서 임의 해시에 따라 발생하는 추가 결함을 찾았다. hidden base token/revision,
엔진의 실행/가게 번호·사진 SHA·납품 manifest·피드백 참조를 고객 문장과 같이 최소화하면
숫자열이 전화번호 marker로 바뀌어 저장 또는 납품 검증이 실패했다.
수정본 metadata는 필드 검증을 거쳐 그대로 보존하고, 사진/피드백 입력은 strict typed parser가
설명·사유를 처리하면서 식별자를 보존한다. 엔진 native builder는 자유문자를 조립 전에 처리하고
완성된 구조 기록을 다시 문장처럼 마스킹하지 않는다. 모델/파일 원문 최소화는 유지한다.
고정된 phone-shaped SHA/revision/run/client ID와 피드백→다음 학습 문맥의 회귀로 확인한다.

## 실제 브라우저와 ZIP

## 남은 경계

직접 수정은 확인한 사실 안에서만 사용한다. 새 가격·혜택·기간은 새 사실 확인이 필요한 요청이다.
명시적인 모델 재작성, 웹 사진 업로드, 기간·상태 보관함은 G20 후속 작업이다.
실제 한글 IME·보조기기 사용자 검증과 실제 사장님 과제 성공률은 별도 관측 과제다.
단일 저장소/SQLite worker의 처리량 한계, 버전 100개 상한, 자동 보관/삭제 미정, 관리자 파일 접근 신뢰 경계를 유지한다.
저장소 관리자에 의한 DB와 파일의 동시 위조를 방지하는 별도 격리 서비스는 제공하지 않는다.

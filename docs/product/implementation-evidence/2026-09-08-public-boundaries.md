# 계정 권한·오류 입력·진단 원장 경계 보완

## 한 장 요약

요청 처음의 계정 상태만 믿고 저장하던 경로, 확인/검색/재작성 오류 화면의 비밀값 반영, 생성기 예외의 고객 연락처 저장을 재현하고 공통 경계를 보완했다. **통합 전체 검사 599개 통과·Windows 심볼릭 링크 권한 1개 건너뜀(1166.97초). G22 전체 완료 판정은 아니다.** G21과 분리한 작업 사본의 22개 파일을 기준 SHA와 대조해 합쳤고, 추가 수신·URL 검사를 포함한 변경 소스/테스트 27개의 바이트를 고정해 검증했다. G21의 `ba665e2` 뒤에 이어지는 PR #14의 후속 구현 범위다.

## 구현과 재현

- `services.fresh_actor`는 저장 트랜잭션 안에서 현재 활성 계정을 DB에서 다시 읽는다. 생성·사진 저장·편집/복원·원본/수정본 승인·재작성·취소·온보딩은 현재 가게/작업 권한을 다시 확인한 뒤 저장하거나 동일 요청을 반환한다. 웹 전용 서비스는 actor가 필수이며 worker/CLI의 기존 내부 실행과 구분한다.
- 최초 가게 조회 뒤 계정을 비활성화해도 Job이 접수되는 302 응답을 재현했다. 계정 비활성화·소유권 이전·운영 권한 철회를 주입한 집중 검사에서는 저장·추가 사용량을 거절하고 정상 요청/재전송을 보존했다. 이는 DB 변경을 지정된 시점에 주입한 검사이며 실제 운영의 동시 요청 부하 관측은 아니다.
- 이미 승인한 수정본의 재전송과 재작성 출처 확인 뒤에 `Job.inputs`/`Store.client`가 바뀌면 기존 경로가 성공할 수 있었다. 두 분기에서도 엔진 입력·웹 입력·client 연결을 비교한다. 기존 관리자 화면은 client 변경을 막으므로 일반 사장님이 실행한 권한 우회로 보고하지 않는다.
- OnboardingConfirmForm·ArchiveForm·RewriteForm은 검증된 필드만 오류 화면에 다시 바인딩한다. ChoiceField 오류 메시지도 고정 문구로 바꿔 잘못된 선택 값이 오류 설명으로 반영되지 않게 했다. 정상 날짜·revision·선택 값·서명은 보존한다.
- 생성기가 예외를 던지면 기존 `redact`만으로는 전화번호·이메일이 오류 원장에 남았다. `safe_diagnostic_message`를 `mark_step_failed`와 `record_event`의 자유 설명에만 적용한다. 실행/단계/이벤트 ID와 payload의 구조 값에는 일반 문장 마스킹을 추가하지 않는다. 과도한 JSON 중첩은 고정 안전 문구로 기록해 실패 처리 자체가 중단되지 않게 한다.
- 종료 boundary 없이 끊긴 사진 multipart도 사진 없는 Job으로 접수되는 기존 302를 실제 DB에서 재현했다(기대 400, 1.332초). 수신 핸들러가 파일 1장·20 MiB를 제한하고 크기 초과/중단은 전체 요청 실패로 처리한다. 알려진 파일 오류는 원문 없는 고정 복구 안내를 제공한다. Django 임시파일 처리와 요청 종료 정리를 재사용해 파싱·읽기 오류에서도 현재 업로드 파일을 닫는다.

## 권한·보관의 관측 범위

최초 URL 권한 검사에서 거절되면 원천 검증/파일 접근에 도달하지 않는다. 처음에는 허가됐지만 저장 직전에 권한이 철회된 경우에는 트랜잭션 전에 내부 원본 검증을 이미 했을 수 있으며 최종 쓰기와 내용 제공을 차단한다. 이미 전달한 파일을 사후 회수하는 기능은 없다. 취소 의도는 worker 실행 잠금과 별도로 짧은 DB 트랜잭션에 저장한다.

사진을 저장한 뒤 Job 접수 전에 소유권이 바뀌는 주입 검사에서는 Job·사용량은 추가되지 않으며 정규화 사진 한 개가 남는다. 온보딩 파일 승격 뒤 권한 변경도 잔여 파일이 남을 수 있다. 이를 실패와 별도로 관리할 보관 대상에 포함하며 자동 삭제하지 않는다.

사진 상한은 핸들러가 받은 파일 바이트 기준이다. 전체 multipart 전송 바이트·수신 시간·프록시/WSGI의 선행 버퍼·동시 요청의 총 디스크 한도는 별도 운영 설정이다. 읽기 오류 500은 안전한 정리/무접수 검증이며 정상 업로드 성공으로 세지 않는다. 세션 폐기의 후속 확인은 delivery GET/download POST이며 진행 중인 응답 스트림을 사후 중단하는 검사가 아니다.

기존 G21 합성 가게 한 개를 SQLite `mode=ro`로 읽어 Job 1개·게시 정정 원장 3개와 FK 관계·입력의 사진 참조를 목록화했다. 두 DB 본체 SHA는 전후 같았다. `artifacts/real-use-review/g22-storage-inventory.json`은 현재 웹/엔진 입력만 대조한 관측이다. 여러 가게의 삭제 후보 격리, 모든 스냅샷·백업·지원 사본, 실제 보관 기한/삭제·공급자 처리는 완료하지 않았다. Django PROTECT 정책과 SQLite NO ACTION 제약도 구분한다.

## 구현과 재현

- **기존 성과 원장과 출처:** `.aicmo/runs.sqlite3`의 `manual_outcomes`·`manual_outcome_imports`를 계속 사용한다. 수기 입력도 `DailyOutcome` 검증과 결정적인 CSV 바이트를 거쳐 기존 미리보기·확인 SHA·원자적 정정 계약으로 저장한다. 현재 성과행에는 nullable `input_kind`·`recorded_at`·`recorded_by`를 추가하고 과거 행의 알 수 없는 출처는 비워 둔다. 같은 숫자의 재전송에는 새 수정번호·기록 시각을 붙이지 않으며 기존 v1 확인·보고 SHA도 보존한다.
- **수기·CSV 확인과 복구:** 날짜·한 주·채널·네 지표를 native HTML 폼으로 받고 기존값과 입력값을 대조한다. 새 날짜가 모두 빈칸이면 관측행을 만들지 않는다. 기존 값을 빈칸으로 지우는 것은 명시적 정정이며 CSV에서 생략한 날짜는 보존한다. 날짜 선택과 ‘다시 입력’은 유효한 수기 숫자를 복원한다. 잘못된 토큰·파일명·입력 원문을 오류에 재표시하지 않는다.
- **확인·수신·권한 경계:** 15분 서명 토큰이 계정·가게·client·주차·채널·입력 종류·원본 SHA·확인 SHA를 묶는다. 저장 직전에 현재 계정과 가게 권한을 다시 검사한다. Django가 해석한 CSV 미리보기 URL에서 기존 단일 업로드 핸들러의 파일 수신 상한을 32 KiB로 제한한다. MIME·파일명·폼 값으로 상한을 바꾸지 못하며 사진의 20 MiB·한 파일·중단 수신 실패·임시파일 정리 계약은 유지한다.
- **미입력과 부분합:** SQLite `mode=ro`의 같은 읽기 트랜잭션에서 이번 주와 지난주를 가져온다. 부분합과 입력 N/7일을 표시하며 양쪽 모두 7일을 기록했고 지난주 합계가 양수일 때만 증감률을 낸다. G21의 ‘게시했다고 기록한 문안’은 일별 `posts`에 자동 합산하지 않는다. 새 DB·중복 성과 모델·외부 수집은 추가하지 않았다.
- **세 가지 고정 작업과 기존 호출자:** Job에 `local-store-pack`·`weekly-report`·`local-pack-feedback` 종류와 DB 제약을 추가했다. 기존 행의 기본값은 실행팩이다. 가게별 동일 제출 키·진행 중 한 작업·worker 잠금·취소·복구를 재사용한다. 보고서·피드백 작업 ID는 팩 편집·사진·ZIP·게시 기록 URL과 직접 서비스 호출에서 거절한다. 사진과 수정본 승인 재전송은 실제 엔진 run의 workflow도 대조한다.
- **확인 당시 숫자로 고정한 보고서:** 새 접수는 현재 권한의 서버 원장에서 스냅샷을 다시 읽고 서명된 확인 digest와 비교해 Job에 저장한다. 임의 숫자와 재계산 SHA만으로 보고서를 접수하지 않는다. 접수 뒤 원장이 정정돼도 해당 보고서는 접수 시 숫자를 사용한다. 같은 제출의 재전송은 원래의 검증된 스냅샷을 반환하고 새 요청은 최신 원장과 비교한다. `verified_delivery`로 검증한 정확한 보고서 바이트만 조회·파일 저장에 제공한다. 정정돼 오래된 보고서와 현재 원장을 읽을 수 없는 상태를 구분한다.
- **구형 실행과 구조 값:** `weekly-report`의 선택 입력 `outcomes_snapshot_json`이 아예 없는 구형 실행에서만 새 선택 선언을 digest 계산에서 제외한다. 다른 입력·단계·프롬프트 변경을 무시하지 않는다. 선택 입력이 존재하면서 빈 문자열·null·잘못된 JSON이면 현재 원장 읽기로 대체하지 않고 거절한다. JSON 중복 키·날짜·행 수·범위를 검증하고 구조 ID·SHA는 일반 문장 개인정보 마스킹으로 훼손하지 않는다.
- **작은 다음 행동:** 검토된 보고서의 고정 숫자와 입력 일수로 최대 세 가지 행동을 제공한다. 기록 확인·기존 소식 확인·실제 새 소식 입력의 기존 화면으로 이어지며 숫자의 증감에서 새 사업 사실을 만들지 않는다. 선택·거절은 기존 events의 타입 검증된 영수증 하나로 저장한다. 보고 파일 SHA·스냅샷 SHA·요청 키를 대조하고 같은 요청은 같은 영수증으로 처리한다. 선호를 실제 게시·성과·문안 사용·KB 학습으로 기록하지 않는다.
- **실제 문안 피드백과 명시 반영:** 승인 묶음의 실제 문안과 파일 SHA를 확인하고, 선택한 경우 같은 가게·naver·관측 주에 맞는 검토된 보고서 파일의 실제 SHA를 연결한다. 최근 보고서 최대 20개를 살피며 전체 검토 근거가 6,000자를 넘으면 잘라 쓰지 않고 거절한다. 후보의 실제 바이트 SHA를 사장님 승인에 묶고 worker의 terminal reviewer PASS 뒤 별도의 반영 POST가 기존 승인 피드백 KB를 갱신한다. 후보 승인과 반영 직전에는 현재 가게 PK·client·입력·계정 권한을 다시 대조한다. 상태 조회는 유효한 승인 영수증과 정확한 KB 블록을 읽을 뿐 새 반영을 만들거나 복구하지 않는다.
- **사진을 고르지 않은 다음 팩 요청:** 실제 브라우저의 빈 FileInput이 `filename=""` multipart로 전달돼 사진 없는 요청까지 400으로 거절되는 문제를 재현했다. 실제 파일이 없고 `photo`가 단일 빈 문자열인 경우만 기존 폼의 허용 필드에 포함하도록 두 줄을 보완했다. 중복 필드·비어 있지 않은 가짜 파일 값·실제 업로드 검증은 유지한다. raw multipart 회귀 후 같은 브라우저에서 다음 팩 요청을 다시 확인했다.
- **최초 SQLite 연결 경합과 정리:** 첫 전체 회귀에서 WAL 설정 잠금 경합과 이후 누수된 연결의 ResourceWarning을 확인했다. 공통 DB 연결에서 설정부터 `finally: close()` 안에 두고, WAL 조회·전환 단계는 SQLite primary 오류 코드의 하위 8비트가 `SQLITE_BUSY`인 경우에만 하나의 5초 예산 안에서 재시도한다. 일반 오류를 잠금 오류로 바꾸지 않고 read-only 연결에는 WAL 설정을 실행하지 않는다. schema 확인·DDL·이관은 `BEGIN IMMEDIATE` 한 트랜잭션으로 묶어 동시 초기화와 부분 실패를 처리한다. 첫 보완 검사에서도 동시 import 한 건이 실패해 재검토했고, 확장 BUSY 코드 판별과 최종 집중 검사를 추가했다. 최초 실패의 실제 확장 오류 코드 숫자는 관측되지 않았으므로 특정 코드였다고 단정하지 않는다.
- **경쟁 검사의 자식 시작·파이프 정리:** 테스트의 자식 준비 10초 제한과 실패 시 파이프 네 개의 누수를 수정했다. Windows의 시작 대기는 60초로 두고 실제 잠금 시도/획득 신호로 경쟁 경계를 확인한다. 시간 초과에서도 자식/파이프를 정리한다. 이는 테스트 harness의 검증 신뢰성을 보완한 것이며 제품의 provider 시간 제한을 늘렸다는 의미가 아니다.

주요 경로는 `src/aicmo/outcomes.py`, `schema.py`, `db.py`, `spec.py`, `source_input.py`, `step_executor.py`, `runner.py`, `learning.py`, `store_app/outcome_services.py`, `report_services.py`, `action_services.py`, `feedback_services.py`, 관련 뷰·템플릿, `services.py`, `models.py`, `management/commands/work.py`, `forms.py`, `uploads.py`다. 별도 큐·성과 원장·학습 프레임워크·의존성을 추가하지 않았다. 사장님 흐름과 운영 조건은 [앱 실행 안내](../../STORE_APP.md)의 숫자 기록·보고·피드백 절과 함께 읽는다.

## 권한·보관과 미완료 범위

웹 권한 트랜잭션 동안 엔진 원장 저장을 수행하지만 두 SQLite DB 사이의 분산 원자성을 제공하는 것은 아니다. 엔진 저장 뒤 응답을 확인하지 못하면 같은 확인 요청으로 재시도하도록 안내한다. 파일 수신 상한은 프록시의 선행 버퍼·전체 요청 바이트·수신 시간·동시 디스크 상한을 대신하지 않는다. 이미 내려받은 보고서나 승인 문안 사본을 사후 회수하는 기능도 없다.

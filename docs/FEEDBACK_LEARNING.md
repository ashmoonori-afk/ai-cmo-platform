# 한 장 요약

승인된 가게 실행팩의 문안 한 건에 대해 사용 여부와 수정 이유를 기록하고, 검토된 제안을 다음 문안에 반영합니다. 운영자는 실제 보고 내용을 JSON 파일로 입력하고 후보를 확인한 뒤 승인합니다. 기존 `run --feedback`은 일반 피드백 메모이며 이 승인 학습 흐름과 별개입니다.

## 1. 기록 준비

`examples/pack-feedback.json`은 합성 예시입니다. source_run_id는 실제 owner 승인과 최종 reviewer PASS가 끝난 local-store-pack 실행 ID로, observed_on은 실제 관측일로 바꿉니다. 예시의 채택/수정 사실을 실제 고객 결과로 제출하지 않습니다.

| 필드 | 의미 |
|---|---|
| item | 실제 팩의 news-1.txt~news-2.txt 또는 reply-1.txt~reply-5.txt 중 한 건 |
| adoption | used(사용했다고 보고), not_used(미사용 보고), not_recorded(사용 여부 기록 없음) |
| reason | 그 문안을 사용/미사용한 이유. 수정했다면 원본과 최종 문안 차이의 이유도 작성 |
| insight | 다음 생성의 길이·톤·CTA 등에 반영할 구체적 제안 |
| weekly_report_run_id | 선택 사항. 같은 가게·네이버·관측일이 포함된 주의 최종 검토된 weekly-report ID. 없으면 null |

입력은 UTF-8/BOM JSON 최대 8 KiB이며 중복 키·잘못된 날짜·미지원 항목은 거부합니다. reason과 insight는 각각 저장 전 지원 개인정보/시크릿 최소화 후 최대 500자입니다. 자유 서술의 모든 개인정보를 자동 인식하지 않으므로 이름·연락처 대신 필요한 요약만 입력합니다.

관측일은 원본 실행 생성일(UTC 저장 시각을 한국 시간으로 변환한 날짜)부터 오늘까지입니다. 문안 생성 전의 채택 기록은 입력할 수 없습니다. 후보 전체가 완전한 검토 범위인 6,000자를 넘으면 짧은 원문으로 새 팩을 만들어 기록합니다.

원본은 승인 대기 시점의 실제 산출물 해시와 대조해 `.aicmo/snapshots/`에 저장한 바이트입니다. 과거 실행에 이 검증 기록이 없으면 현재 문안을 원본으로 추정하지 않습니다. 현재 워크플로우로 새 팩을 만들어야 합니다. 기존 `_pre_edit/` 사본은 보존합니다.

## 2. 후보 검토와 반영

실제 입력을 `feedback.json`에 저장한 뒤 실행합니다. 아래 sample-client-a와 feedback-01은 예시 가게·새 실행 ID이며 운영 중인 가게와 사용하지 않은 ID로 지정합니다.

```powershell
uv run aicmo run local-pack-feedback --client sample-client-a --feedback-file feedback.json --run-id feedback-01 --review codex
uv run aicmo approve feedback-01 owner_gate --reviewer owner --notes "보고한 사실과 다음 반영 제안을 확인함"
uv run aicmo resume feedback-01 --review codex
uv run aicmo learn-feedback feedback-01
```

첫 명령은 `artifacts/feedback-01/feedback.json`에 원본·승인 문안, 실제 변경 여부, 보고한 채택/이유, 제안 및 선택한 주간 보고서를 저장하고 owner 승인을 기다립니다. 승인 전에 이 파일 전체를 확인합니다. 수정할 사항이 있으면 입력 JSON을 고쳐 새 feedback 실행을 생성합니다. candidate 파일을 직접 수정한 뒤 승인하는 방식은 원래 입력/증거와 달라 반영이 거부됩니다.

최종 semantic reviewer PASS가 있어야 learn-feedback이 작동합니다. WARN·FAIL·demo·잘린 근거·파일 변경·다른 가게/기간·현재와 다른 명세는 반영할 수 없습니다. 사용 가능한 리뷰 실행기는 `run --help`의 --review 또는 --review-cmd를 따릅니다. 공급자나 로컬 리뷰 실행기의 실제 성공은 별도 환경 검증이 필요합니다.

## 3. 다음 생성과 복구

learn-feedback은 파일을 append하고 정확한 블록을 확인한 뒤 SQLite에 반영 완료를 기록합니다. 같은 증거를 재전달해도 블록/기록은 한 건입니다. 파일 저장 후 DB commit 전에 중단됐다면 같은 입력으로 재시도합니다. 파일/권한 오류는 기존 파일을 보존하고 원인을 해소한 뒤 재시도합니다. KB 블록을 직접 고치면 다음 생성에서 제외되므로 정정은 새 피드백의 검토·승인 흐름으로 남깁니다.

같은 증거를 새 feedback 실행에서 다시 검토·승인해 반영하면 KB 블록은 늘리지 않고 최신 유효 실행을 검증 근거로 사용합니다. 이전 feedback 산출물이 손상되어도 새 실행의 완전한 검증 근거가 남아 있으면 이를 사용할 수 있습니다.

같은 팩·문안의 다른 제안을 새로 검토·반영하면 다음 생성에는 가장 최근의 유효한 제안 한 건을 선택합니다. 이전 KB 기록은 삭제하지 않습니다. 과거의 동일 증거를 재전달하는 것만으로 최신 정정을 덮어쓰지는 않습니다.

최신 제안의 증거가 손상되면 이를 제외하고 이전의 유효한 제안으로 돌아갑니다. context에는 유효하지 않아 제외한 수와 최신 제안으로 대체된 수가 각각 표시됩니다. 유효한 5개를 찾으면 검사를 멈추므로 이 수치는 실제 검사한 범위의 집계입니다. 최근 20개 전체의 총계는 아닙니다. 파일 변조를 선호 삭제 수단으로 사용하지 않습니다.

새 local-store-pack의 `learning-context.json`은 같은 가게의 최근 후보 20개 중 현재 원본/최종 승인·주간 보고서·KB 블록까지 검증되는 최대 5개를 담습니다. drafts가 이 파일을 입력으로 소비하고 현재 사실·브랜드 지침을 우선합니다. 일반 KB 문장이나 운영 상태 큐는 학습으로 읽지 않습니다. 기존 생성 실행의 성공한 context는 스냅샷으로 남으며 새 피드백 반영을 보려면 새 실행을 만듭니다.

이 기능은 모델 자체를 훈련하지 않습니다. 사용자 보고에 근거한 검토된 선호를 다음 생성의 문맥에 전달합니다. 실제 외부 게시·가게 소유권·매출 인과를 인증하지 않으며 유료 운영이나 실제 고객 효과의 증거가 아닙니다. G02는 OPEN입니다.

## 다음 단계

1. 운영자는 실제 채택/수정 사례 한 건의 입력과 후보를 대조하고 정확한 버전을 승인합니다.
2. 개발자와 reviewer는 새 팩의 learning-context와 문안을 확인해 승인된 제안의 반영 여부를 검토합니다.
